# cursor-discord-channels v0.2 — warm ACP session (iteration + benchmark)

## The iteration in one line
**v0.1 cold-spawns `cursor-agent` once per Discord message (~10–12s each, no memory). v0.2 holds one warm `cursor-agent acp` session — ~7× faster after the first turn, and it remembers.**

## v0.1 (current `main`)
The bridge runs `cursor-agent -p "<message>"` once per Discord message. Every message pays a cold start: binary init + MCP handshake + re-reading the conversation context. On the droplet that's **~10–12s per message**, and there's **no shared memory** across messages — each spawn is a fresh process.

## v0.2 (this iteration)
The bridge holds **one warm `cursor-agent acp` session** and sends each Discord message as a prompt into it. The cold-start cost is paid **once**; subsequent turns are warm and share a single coherent context.

## The discovery that unlocked it
Cursor Agent officially exposes a persistent server: **`cursor-agent acp`** runs the agent as an **ACP (Agent Client Protocol)** server — JSON-RPC over stdio: `initialize` → `session/new` → `session/prompt` → streamed responses. That is the "warm harness" — no PTY hacks, no terminal screen-scraping. It's the same role Claude Code's `--channels` runtime plays, just reachable as a standard, documented protocol.

## What we measured
Droplet `genius-team-v2`, model `composer-2.5`, a minimal hand-written ACP client.

**1. The pipe works.**
`initialize` → `session/new` (returns a `sessionId`) → `session/prompt("Reply PONG")` → streamed `agent_message_chunk` (`'P'`, `'ONG'`) → `stopReason: end_turn`. Clean, structured response.

**2. Shared memory across turns (one session).**
- Turn 1: *"Remember: the magic word is BANANA."* → *"Got it — the magic word is BANANA."*
- Turn 2 (same session): *"What is the magic word?"* → *"BANANA."*

One coherent context — it remembers, instead of forgetting between messages.

**3. The speedup.**

| | per-message latency |
|---|---|
| v0.1 — cold spawn (`agent -p` per message) | **~10–12s every message** |
| v0.2 — warm session, turn 1 (one-time warmup) | 10.7s |
| v0.2 — warm session, turn 2+ (steady state) | **1.5s** |

**~7× faster on every message after the first.** The cold-start tax (binary init + session setup + context load) is paid once, not per message. (Measured on short prompts; longer answers still take longer to *generate*, but the ~9–10s startup tax is gone for good.)

## Why it matters
The agent was answering last on Discord despite running a fast model — purely because of the cold-spawn-per-message architecture. Warming the session fixes the root cause: **coherent cross-channel memory + ~7× faster responses.**
